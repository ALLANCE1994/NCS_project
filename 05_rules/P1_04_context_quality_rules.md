# 上下文质量规则

> **文档编号**：NV-RULE-CONTEXT-001
> **版本**：V1.0
> **生效日期**：2026-05-18
> **核心原则**：结构化输入产生交付型输出

---

## 一、结构化输入标准

### 1.1 必须包含的要素

| 要素 | 说明 | 示例 |
|------|------|------|
| **任务目标** | 一句话明确要做什么 | "编写频率范围100kHz-10MHz的脉冲发生模块" |
| **知识来源** | 明确参考文档 | "基于《脉冲卡技术手册》第3章" |
| **改动边界** | 明确允许改什么、禁止改什么 | "仅处理脉冲模块，不涉及时序约束" |
| **参数约束** | 具体参数范围 | "频率精度：1Hz，占空比：1%-99%" |
| **输出要求** | 交付物清单 | "VHDL代码 + XDC约束 + 测试用例" |
| **验收标准** | 如何验证完成 | "编译通过 + 时序满足 + 功能仿真通过" |

### 1.2 结构化输入模板

```markdown
@目标智能体 请完成以下任务：

【任务目标】一句话描述要做什么（明确、具体）
【知识来源】请基于《XXX文档》第X章 / 项目知识库中的XXX内容
【改动边界】仅处理XXX，不涉及YYY
【参数约束】具体参数范围：XXX
【输出要求】交付物清单：XXX
【验收标准】如何验证完成：XXX
【禁止事项】不进行XXX操作

请先确认理解，再开始执行。
```

### 1.3 禁止的输入方式

| 禁止方式 | 幻觉风险 | 正确方式 |
|----------|---------|----------|
| "帮我写一个XXX" | 无边界，AI可能编造 | "请基于XXX文档，编写参数范围为...的模块" |
| "参考一下其他方案" | AI可能套用不相关方案 | "请仅参考本项目知识库中的XXX方案" |
| "大概就行" | AI可能随意发挥 | "请严格按照XXX标准执行" |
| "你看着办" | AI可能做出错误假设 | "请按以下步骤执行：1)... 2)..." |
| "用最好的方案" | "最好"无定义 | "请使用满足XXX约束的最简方案" |

## 二、交付型输出标准

### 2.1 必须满足的条件

| 条件 | 说明 | 验证方法 |
|------|------|----------|
| **可运行** | 代码可直接编译/运行，无语法错误 | 编译/运行测试 |
| **可验证** | 有明确的验证方法和测试用例 | 执行测试用例 |
| **可追溯** | 标注知识来源，可追溯到原始文档 | 检查知识来源标注 |
| **可回滚** | 每个改动可独立回滚 | git revert测试 |

### 2.2 输出格式要求

所有技术输出必须包含：

```markdown
【核心内容】
代码/设计/方案

【知识来源】
- 文档名称：《XXX》
- 核心出处：第X章

【验证方法】
- 测试用例：XXX
- 验证步骤：XXX

【回滚方案】（如涉及代码修改）
- 回滚方式：L1/L2/L3
- 回滚命令：XXX
```

## 三、与@A的配合关系

### 3.1 规则层面（本文件）

- 定义**结构化输入的标准格式**
- 定义**交付型输出的验收标准**
- 定义**禁止的输入方式**
- 作为全局规则依据

### 3.2 执行层面（@A职责）

@A依据本规则执行以下职责：

| @A职责 | 依据本规则 |
|--------|-----------|
| 指令精准化服务 | 将模糊指令转换为结构化输入格式 |
| 幻觉预警机制 | 识别禁止的输入方式并预警 |
| 无幻觉提问模板 | 提供结构化输入模板 |
| 避坑要点告知 | 告知禁止的输入方式 |

### 3.3 配合流程

```
用户下达指令
    │
    ▼
@A检查指令质量（依据本规则）
    │
    ├─ 指令符合结构化标准 → 直接下发执行
    │
    └─ 指令不符合标准 → 预警 + 提供修正建议 → 用户修正后下发
```
