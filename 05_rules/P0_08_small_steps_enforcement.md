# P0_08 小步快跑强制执行

> **规则优先级**：P0（最高优先级）  
> **生效日期**：2026-05-19  
> **制定人**：@C老板  
> **执行人**：@V 工程规则管理师 / 各开发智能体  
> **适用范围**：所有代码开发任务

---

## 一、规则目的

防止"一步到位"式开发导致的系统性风险，通过小步快跑、快速验证的方式，确保每步都可控、可回滚、可验证。

---

## 二、规则内容

### 2.1 代码量限制（强制）

```
单步修改不超过50行代码
├── 超过50行 → 必须拆分为多步
└── 每步独立验证 → 通过后再下一步
```

### 2.2 明确验证目标（强制）

每步必须有明确的验证目标：

| 步骤类型 | 验证目标示例 |
|----------|--------------|
| 端口定义 | 语法正确、综合无ERROR |
| 逻辑实现 | 功能仿真通过 |
| 约束添加 | 综合通过、时序满足 |
| 模块集成 | 接口匹配、无冲突 |

### 2.3 合规检查（强制）

每步必须通过@V合规检查：

```
编码完成 → 自验证 → @V检查 → 通过 → 下一步
    ↑___________________________|
         （不通过返回修改）
```

### 2.4 禁止一步到位（强制）

| 禁止行为 | 正确做法 |
|----------|----------|
| 一次性完成整个模块 | 分步：端口→逻辑→约束→验证 |
| 一次性添加所有约束 | 分步：时钟→输入→输出→虚假路径 |
| 一次性修改多个模块 | 分步：逐个模块验证 |
| 无验证即下一步 | 每步必须验证通过 |

## 四、执行流程

### 4.1 标准开发流程

```
Step 1: 准备
├── 明确本步目标
├── 预估代码行数（≤50行）
└── 确定验证方法

Step 2: 开发
├── 编写代码（≤50行）
└── 自测验证

Step 3: 提交
├── 代码审查申请
├── @V合规检查
└── 问题修复

Step 4: 通过
├── @V签字确认
├── 代码入库
└── 进入下一步
```

### 4.2 代码行数统计方法

```bash
# 统计新增/修改行数（不包括空行和注释）
git diff --stat
# 或
git diff | grep -E "^\+[^+]" | wc -l
```

### 4.3 特殊情况处理

| 情况 | 处理方式 |
|------|----------|
| 必须超过50行 | 拆分为逻辑子步骤，每步独立验证 |
| 紧急修复 | 同样需要@V快速审核（≤30分钟） |
| 重构代码 | 分文件/分函数逐步重构 |

## 六、违规处理

| 违规情况 | 处理措施 |
|----------|----------|
| 单步超过50行 | 要求拆分，重新验证 |
| 无验证即下一步 | 暂停开发，补验证 |
| 未通过@V检查 | 退回修改 |
| 隐瞒验证结果 | 记录违规，通报批评 |

## 八、最佳实践

### 8.1 如何拆分大任务

```
任务：实现DDS模块（预估200行）

拆分方案：
├── Step 1: 端口定义（20行）
```
