## MVP裁定四步算法

### Step 0：第一动作唯一性检查（前置条件）

- 必须回答：MVP是否只有一条灵魂路径？
- 必须回答：是否存在多条并行路径？（若存在，必须砍到只剩一条）
- 必须回答：用户进入系统后，第一个动作是否唯一且明确？
- 裁决规则：若存在多条并行路径 -> 直接判定"需进一步聚焦，禁止多路径并行"

### Step 1：识别唯一价值交换

- 必须回答：用户主动做的第一件事是什么？
- 必须回答：系统必须立即返回的结果是什么？
- 必须回答：如果去掉该结果，产品是否立即失去存在意义？
- 裁决规则：若无法识别唯一价值交换 -> 直接判定"该PRD不具备MVP条件"

### Step 2：构建最短状态链路

- 约束条件：状态数量 <= 3
- 约束条件：状态必须线性
- 约束条件：不允许分支、不允许并发
- 约束条件：每个状态只能由前一个状态触发
- 裁决规则：任意引入条件判断、并行或分支 -> 视为"超出V1"

### Step 3：映射最小技术动作

- 对每个状态，映射为1个技术操作
- 输入输出必须是基础类型
- 严禁：多表join、异步任务编排、消息队列

### Step 4：风险反向裁剪

- 任一功能满足以下任一条件 -> 必须DEFERRED
- 引入3个及以上状态变更
- 依赖外部系统/SDK/插件
- 需要复杂UI状态或动画
- 需要一致性、回滚、补偿、重试机制

## V1负面清单

- 复杂前端交互动画
- 第三方插件或SDK集成
- 多设备同步
- 复杂权限体系

## 技术冻结协议

- 框架能力：仅允许使用PYNQ原生能力
- 数据结构：单表或键值结构；禁止多级嵌套
- 通信模型：同步优先；AXI Lite优先

## 架构设计中的回滚考虑

- 模块化设计：各模块可独立启用/禁用（配合L1 Feature Flags）
- 接口稳定性：接口定义一旦确定，变更需走L2决策流程
- 配置化参数：关键参数可通过配置修改，避免硬编码
- 版本兼容性：考虑向前兼容性，支持 graceful degradation

## 工程定型阶段出口条件检查清单

- 系统架构图已输出（Mermaid格式，模块关系清晰）
- 接口定义文档已输出（信号、方向、位宽、功能完整）
- PS-PL划分方案已确定（功能边界明确）
- 技术选型文档已完成（选型理由充分）
- @V审核报告已通过
- 检查流程：完成产出物 -> 自检出口条件 -> 提交@V审核 -> 通知@M阶段完成

## 架构决策输出模板

- 核心生存链路 Golden Loop：[状态1] -> [状态2] -> [状态3]
- V1 冻结决议：V1 只做 [具体内容]，V1 不做任何其他事
- DEFERRED 清单：被裁剪的功能模块列表
- 技术选型理由：选择XXX的原因 / 不选择YYY的原因

## 接口定义模板

- 信号名称：信号标识
- 方向：输入/输出/双向
- 位宽：总线宽度
- 功能描述：信号用途说明

## 技术规格下发协议

- PS-PL划分方案：明确PL端和PS端的功能边界、数据通路、时钟域
- 接口定义：明确AXI总线信号、中断、DMA通道等
- 时序与性能约束：关键路径时序要求、吞吐量指标、延迟预算
- 下发方式：通过项目经理的任务分配模板传递，附加架构决策文档作为技术附件

## 科学需求接收转化流程

- 关键参数转化：脉冲宽度 -> 时序精度约束、采样率 -> 数据带宽约束、频率范围 -> PLL配置约束
- 转化流程：物理参数 -> 工程量化指标 -> 架构设计约束
- 知识库交叉引用：scientific_principles目录中的参数标准作为架构输入参考
