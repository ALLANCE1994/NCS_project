# 优化后AI驱动NV色心项目整体运行规范

> **版本**：v2.0
> **更新日期**：2026-05-16
> **适用项目**：NV色心ZYNQ实验系统

---

## 一、总则

### 1.1 项目定位

本项目是一个**AI辅助FPGA科研工程项目**，核心业务架构保持不变：
- ZYNQ7020硬件体系
- 任意波形发生器/脉冲卡/采集卡/锁相放大器四大模块
- PYNQ+Jupyter实验框架
- NV色心整套实验流程
- 硬件开发技术路线

### 1.2 AI团队定位

AI智能体团队是**效率工具**，不是决策主体：
- 人是唯一的舵手，AI是引擎
- AI负责执行，人负责判断方向
- 所有重大决策由客户（人）做出

### 1.3 核心原则

> **想让AI编程可控，你必须先慢下来。慢在前期，快在后期。**

### 1.4 文档处理原则

本项目采用**「通用粗处理 + 专业精提炼」**双层文档加工模式：
- **文档预处理工程师**：唯一拥有PDF读取权限，负责粗加工
- **专业智能体**：仅接收规整初稿，负责深度专业提炼
- **审核入库**：工程规则管理师审核，客户确认后手动投喂知识库


#### 2.1.3 产出要求

| 产出物 | 负责人 | 格式要求 |
|--------|--------|----------|
| 项目DNA | 老板 | 项目DNA模板 |
| 项目计划 | 项目经理 | 任务分解表 |
| 风险评估报告 | 工程规则管理师 | 风险评估模板 |
| V1冻结规范 | 架构师 | V1冻结决议模板 |

#### 2.1.4 验收标准

- [ ] 项目DNA包含价值锚点、第一动作、边界定义
- [ ] Not-To-Do List明确
- [ ] DEFERRED清单完整
- [ ] 风险评估通过三维过滤网

### 2.2 第二阶段：工程定型

#### 2.2.1 启动条件
- 第一阶段产出通过审核

#### 2.2.2 执行流程

```
项目经理分配任务 → 架构师设计架构 → 量子科学家计算参数 → 工程规则管理师审核 → 输出工程蓝图
```

#### 2.2.3 产出要求

| 产出物 | 负责人 | 格式要求 |
|--------|--------|----------|
| 系统架构图 | 架构师 | Mermaid格式 |
| 接口定义 | 架构师 | 表格格式 |
| 实验参数 | 量子科学家 | 参数计算模板 |
| 审核报告 | 工程规则管理师 | 审核报告模板 |

#### 2.2.4 验收标准

- [ ] 架构图清晰展示模块关系
- [ ] 接口定义完整（信号、方向、位宽、功能）
- [ ] 参数计算有公式推导
- [ ] 审核报告通过

### 2.3 第三阶段：工程落地

#### 2.3.1 启动条件
- 第二阶段产出通过审核

#### 2.3.2 执行流程

```
项目经理分配开发任务 → 硬件工程师/软件工程师开发 → 工程规则管理师代码审核 → 项目经理验收 → 老板审批 → 交付
```

#### 2.3.3 产出要求

| 产出物 | 负责人 | 格式要求 |
|--------|--------|----------|
| VHDL代码 | 硬件工程师 | 符合编码规范 |
| XDC约束 | 硬件工程师 | 符合约束规范 |
| Python代码 | 软件工程师 | 符合PEP 8 |
| Jupyter Notebook | 软件工程师 | 符合Notebook规范 |
| 编译报告 | 硬件工程师 | 资源+时序报告 |
| 测试报告 | 软件工程师 | 测试覆盖报告 |

#### 2.3.4 验收标准

- [ ] 代码通过语法检查
- [ ] 代码通过编码规范审核
- [ ] 编译通过，无错误
- [ ] 时序满足要求
- [ ] 测试覆盖核心功能

## 三、智能体工作规范

### 3.1 老板工作规范

#### 3.1.1 审计规则（不可跳步）

| 步骤 | 名称 | 核心任务 |
|------|------|----------|
| 1 | 价值锚点 | 确定核心目标、具体受众、衡量标准 |
| 2 | 第一动作聚焦 | 识别唯一价值交换，做减法 |
| 3 | 边界定义 | 明确Not-To-Do List和DEFERRED清单 |

#### 3.1.2 禁用清单

- "提升用户体验"
- "增强系统功能"
- "优化性能"
- 任何形容词描述

#### 3.1.3 输出规范

必须使用项目DNA模板，包含：
- 一句话定义项目核心价值
- 第一动作路径
- 技术约束
- 功能规格
- Not-To-Do List
- DEFERRED清单

### 3.2 项目经理工作规范

#### 3.2.1 任务拆解原则

| 原则 | 要求 |
|------|------|
| 改动边界 | 明确允许改什么、禁止改什么 |
| 目标状态 | 定义"修到什么程度算完成" |
| 验收方式 | 定义如何验证完成正确 |
| 禁止顺手优化 | 防止修Bug引入新问题 |

#### 3.2.2 并行调度规则

- 最多同时调度3个智能体并行工作
- 并行任务必须相互独立
- 有依赖关系的任务必须串行

#### 3.2.3 进度管理

- 每天更新项目状态
- 每天提交日报
- 每周提交周报
- 延期超过1天立即上报

### 3.3 工程规则管理师工作规范

#### 3.3.1 审核标准（三维过滤网）

| 维度 | 检查项 | 严重程度 |
|------|--------|----------|
| A维：政策红线 | 硬件安全、数据安全、合规性 | 致命 |
| B维：成本黑洞 | 资源使用、开发成本、维护成本 | 高危 |
| C维：工程陷阱 | 时序风险、接口风险、依赖风险 | 中等 |

#### 3.3.2 审核时效

- 所有审核必须在24小时内完成
- 审核结果必须有书面记录
- 不通过的审核必须提供修改建议

#### 3.3.3 一票否决权

- 发现严重违规或安全隐患时，有权立即暂停相关操作
- 有权拒绝任何不符合规范的产出
- 否决理由必须明确、具体、可操作

### 3.4 架构师工作规范

#### 3.4.1 MVP裁定四步算法

| 步骤 | 名称 | 核心任务 |
|------|------|----------|
| 1 | 识别唯一价值交换 | 用户第一件事 + 系统返回结果 |
| 2 | 构建最短状态链路 | 状态数量≤3，线性，无分支 |
| 3 | 映射最小技术动作 | 每个状态映射1个技术操作 |
| 4 | 风险反向裁剪 | 满足条件的必须DEFERRED |

#### 3.4.2 V1负面清单

以下能力在MVP阶段**严禁出现**：
- 复杂前端交互动画
- 第三方插件或SDK集成
- 多设备同步
- 复杂权限体系

### 3.5 硬件工程师工作规范

#### 3.5.1 小步快跑四控制法

| 控制项 | 要求 |
|--------|------|
| 改动边界 | "本次只处理XXX模块，不涉及YYY" |
| 目标状态 | "修改后：时序满足、资源不超过80%" |
| 验收方式 | "编译通过 + 时序报告无违例" |
| 禁止顺手优化 | "不进行任何重构或命名调整" |

#### 3.5.2 安全红线

- **禁止**：IO电平不匹配的代码
- **禁止**：时钟域跨越不做同步
- **禁止**：组合逻辑输出直接驱动IO
- **必须**：所有模块有复位逻辑
- **必须**：所有状态机有默认状态

### 3.6 软件工程师工作规范

#### 3.6.1 TDD红-绿-重构循环

| 阶段 | 任务 |
|------|------|
| RED | 编写失败的测试（定义"靶心"） |
| GREEN | 编写最少代码让测试通过 |
| REFACTOR | 在测试保护下优化代码 |

#### 3.6.2 日志规范

```python
# 入口日志
logger.info("==> 开始执行XXX任务, 参数: %s", params)

# 出口日志
logger.info("<== XXX任务完成, 耗时: %dms", duration)

# 警告日志
logger.warning("XXX操作失败, 正在重试...")

# 错误日志
logger.error("XXX任务失败: %s", str(e), exc_info=True)
```

### 3.7 AI使用工程师工作规范

#### 3.7.1 服务范围

- 指令优化服务
- MTC使用教学
- 专属指令模板定制
- 使用误区预警
- 疑问解答
- 阶段性使用方案
- 方法论沉淀

#### 3.7.2 禁止事项

- **禁止**参与硬件开发决策
- **禁止**参与科学实验设计
- **禁止**参与项目业务审批
- **禁止**修改技术方案
- **禁止**审核业务产出

## 四、项目复盘机制

### 4.1 阶段性复盘

每个里程碑完成后进行复盘：

| 复盘项 | 内容 |
|--------|------|
| 完成情况 | 计划vs实际 |
| 问题回顾 | 遇到的问题及解决方案 |
| 经验沉淀 | 可复用的方法论 |
| 改进建议 | 下阶段优化方向 |

### 4.2 错误预判机制

| 风险类型 | 预判信号 | 预防措施 |
|----------|----------|----------|
| 需求膨胀 | 功能点持续增加 | 严格执行Not-To-Do List |
| 技术债务 | 临时方案增多 | 定期重构，禁止顺手优化 |
| 进度延期 | 任务完成时间超预期 | 及时上报，调整计划 |
| 质量问题 | Bug数量增加 | 加强测试，代码审核 |

### 4.3 经验沉淀机制

- 所有重要决策记录到知识库
- 所有技术方案记录到知识库
- 所有错误和解决方案记录到知识库
- 定期整理和更新知识库

### 6.4 文档处理流程

#### 6.4.1 双层提炼模式

```
客户上传PDF
    │
    ▼
文档预处理工程师（粗加工）
    - 读取PDF、提取文本
    - 删除冗余、清洗格式
    - 识别领域、精准分发
    │
    ▼
专业智能体（精加工）
    - 深度专业提炼
    - 结合项目落地
    - 输出干货文档
    │
    ▼
工程规则管理师审核
    │
    ▼
本地归档存储
    │
    ▼
客户手动确认 → 批量投喂知识库
```

#### 6.4.2 文档分发规则

| 文档类型 | 分发对象 |
|----------|----------|
| NV色心量子传感、ODMR实验、自旋物理 | @量子科学家 |
| ZYNQ/FPGA/Vivado硬件设计 | @硬件工程师 |
| PYNQ、Jupyter、Python上位机 | @软件工程师 |
| 系统顶层架构、整体项目方案 | @架构师 |
| 工程开发规范、流程制度 | @工程规则管理师 |
| AI使用技巧、MTC调度 | @AI使用工程师 |

#### 6.4.3 入库规则

1. **默认不入库**：所有精炼文档默认不自动向量化录入智能体知识库
2. **本地归档**：全部留存本地`01_knowledge_base/`对应目录
3. **手动确认**：由客户手动确认文档可用后，再下达统一指令批量投喂

## 七、智能体工作规范（补充）

### 7.4 文档预处理工程师工作规范

#### 7.4.1 核心职责
- **唯一拥有**：全量PDF读取、文本提取、文件解析、格式初整理工具权限
- **工作内容**：拆文档、清冗余、调格式、分章节、识领域、做分发
- **禁止事项**：技术解读、原理分析、经验总结、专业提炼

#### 7.4.2 处理标准
- **删除内容**：封面、扉页、广告、水印、空白内容、无关附录
- **保留内容**：完整正文、图表基础结构、核心章节
- **输出格式**：层级清晰、排版整洁的Markdown标准初稿

#### 7.4.3 协作约束
- **业务隔离**：不参与项目研发、决策、技术评审
- **单向流转**：PDF → 预处理工程师 → 专业智能体，不可逆向
