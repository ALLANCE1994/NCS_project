---

## 一、核心理念

> **想让AI编程可控，你必须先慢下来。慢在前期，快在后期。**

- **慢在前期**：多画一张图、多写一条规则、多做一次建模
- **快在后期**：改动不再连锁爆炸、Bug能快速定位、新功能可以放心让AI上手
- **慢，是为了让"快"不再失控**

## 二、VibeCoding三阶段方法论

```
[模糊想法]
    |
    v
第一阶段：战略定型（给项目画好边界）
    需求拆解 -> 产品经理Agent -> 风险评估 -> MVP定型 -> 技术选型
    |
    v
第二阶段：工程定型（让AI有可落地的蓝图）
    系统边界&数据流转 -> 架构图自动化 -> 领域建模 -> 数据模型 -> 视觉设计约束 -> Rules驱动开发
    |
    v
第三阶段：工程落地（可控、可调试、可交付）
    环境治理 -> 报错关注模型 -> 小步修改策略 -> Git&回滚 -> TDD驱动 -> 日志&可观测性
    |
    v
[可交付系统 + 可复用的工程路径]
```

### 各阶段核心产出

| 阶段 | 核心任务 | 关键产出 |
|------|----------|----------|
| **战略定型** | 把"想做什么"变成"明确不做什么" | 脱水PRD、风险评估报告、MVP冻结规范 |
| **工程定型** | 从"AI帮我写代码"到"AI在我的工程规则里工作" | 架构图、数据模型、Rules规则集 |
| **工程落地** | 不再害怕AI改代码，随时可停、查、退 | 可运行的系统、测试覆盖、可观测日志 |

## 三、需求拆解方法论

### 3.1 三层需求拆解法

#### 第一性拷问：价值锚点
必须回答三个子问题：
| 维度 | 问题 | 合格示例 |
|------|------|----------|
| 核心目标 | 这个需求到底想达成什么？ | 针对NV色心实验，实现ODMR信号采集与分析 |
| 具体受众 | 为谁、解决何种具体问题？ | 为量子传感研究人员，提供自动化实验控制 |
| 衡量标准 | 创造了何种可验证的业务价值？ | 实验效率提升50%，数据可追溯 |

**禁用清单**："提升用户体验"、"增强系统功能"、"优化性能"等空洞表述。

#### 聚焦性拷问：第一动作聚焦
- **做减法**：弱化甚至隐藏所有次要选项
- **做强推**：所有资源必须像聚光灯一样打在唯一动作上
- **判定标准**：如果需要停顿一秒去思考"我该先做什么"，该规划就是"次品"

#### 纪律性拷问：边界定义
- 明确Not-To-Do List，防止AI诱导式功能膨胀
- 区分V1必须做 vs DEFERRED清单

### 3.2 Not-To-Do List

| 作用 | 说明 |
|------|------|
| **挡住杂念** | 把诱人但次要的功能挡在门外 |
| **约束AI** | 明确告诉AI现阶段边界，AI不懂得"简洁"，只会顺着贪婪往下写 |
| **聚焦资源** | 每一分算力和精力都用在对的地方 |

### 3.3 MVP边界定义法

#### 核心动作路径
MVP边界必须且仅能包围一条灵魂路径。

#### 骨架功能定义
只做那些"撑起房顶"的事：
| 骨架 | 说明 | 原则 |
|------|------|------|
| **核心链路** | 系统的命脉，必须稳定 | 让AI集中精力把核心链路做稳 |
| **数据持久化** | 数据必须可追溯 | 账本不乱，项目就有活下去的本钱 |
| **基础UI** | 能输入、能显示的界面 | 别让CSS圆角和渐变分散AI对核心逻辑的注意力 |

#### DEFERRED清单
每个被砍掉的功能点，都是在为项目成功上线增加一分胜算。

## 四、Agent提示词工程

### 4.1 提示词四步构建法

| 步骤 | 名称 | 核心任务 | 关键原则 |
|------|------|----------|----------|
| 1 | **身份建模** | 定义Agent的人格标签 | 拒绝平庸的"默认值"，赋予权力感和专业底线 |
| 2 | **注入灵魂准则** | 将核心方法论固化为Agent的本能 | 把"拒绝"逻辑化，设定可执行的判断规则 |
| 3 | **Few-shot调教** | 用真实案例教会Agent行为尺度 | 展示"什么是好，什么是烂"，而非只给口头指令 |
| 4 | **输出约束** | 定义产出的格式和内容规范 | 禁用模糊词汇，规定必须输出的模块结构 |

### 4.2 身份标签设计

| 维度 | 思考 | 操作 |
|------|------|------|
| 权力感 | Agent需要有能力"拒绝"用户 | 贴上"铁腕"、"冷酷"等标签 |
| 专业性 | Agent需要懂系统复杂度 | 贴上"技术型"、"架构师"等标签 |
| 对抗性 | Agent需要主动找问题 | 设定为"悲观主义"、"职业黑粉" |

### 4.3 链式调用模式

```
[用户原始需求]
    |
    v
[铁腕PM] -- 需求审计、逻辑脱水 --> [脱水PRD]
    |
    v
[风险评估专家] -- 三维风险扫描 --> [风险评估报告]
    |
    v
[极简主义架构师] -- MVP边界裁定 --> [V1冻结规范]
    |
    v
[Builder/SOLO模式] -- 在明确边界内编码 --> [可交付系统]
```

## 五、Rules驱动开发

### 5.1 Rules四类分类法

| 类别 | 核心目标 | 典型Rule示例 |
|------|---------|--------------|
| **第一类：编码习惯** | 减少选择题，让代码风格统一 | VHDL命名规范、文件目录约定、统一错误处理结构 |
| **第二类：项目结构** | 控制项目不变形，防止腐烂 | 模块只负责单一功能、禁止复制相同逻辑 |
| **第三类：安全红线** | 避免致命风险，项目可以慢但不能炸 | 禁止IO电平不匹配、所有模块必须有复位逻辑 |
| **第四类：交付自检** | 让AI自己当QA，质检思维前移 | 生成代码后必须自检时序/资源/安全 |

### 5.2 Rule有效特征

| 特征 | 无效Rule | 有效Rule |
|------|----------|----------|
| **可执行性** | "注意性能，避免慢查询" | "所有列表查询必须分页，默认不超过50条" |
| **具体性** | "优先使用Server Component" | "默认使用Server Component；涉及输入、滚动、订阅的场景允许使用Client Component" |
| **无歧义** | "遵循最佳实践" | "所有服务函数返回统一结构：{ ok, data, error }" |

## 六、小步快跑策略

### 6.1 四控制法

| 控制项 | 说明 | 正确做法 |
|--------|------|---------|
| **改动边界** | 明确允许改什么、禁止改什么 | "本次只处理XXX模块，不涉及YYY" |
| **目标状态** | 定义"修到什么程度算完成" | "修改后：时序满足、资源不超过80%" |
| **验收方式** | 定义如何验证修复正确 | "编译通过 + 时序报告无违例" |
| **禁止顺手优化** | 防止修Bug引入新问题 | "不进行任何重构、命名调整或抽象优化" |

## 七、TDD驱动开发

### 7.1 红-绿-重构循环

```
RED（红）──→ GREEN（绿）──→ REFACTOR（重构）
    ↑                              │
    └──────────────────────────────┘

RED     - 编写失败的测试（定义"靶心"）
GREEN   - 编写最少代码让测试通过（先让它工作）
REFACTOR - 在测试保护下优化代码（再让它优雅）
```

| 阶段 | 角色 | 核心任务 |
|------|------|---------|
| **红** | 开发者主导 | 将需求翻译为必然失败的自动化测试 |
| **绿** | AI高效执行 | 编写最少代码让测试通过 |
| **重构** | 人机协作 | 在测试安全网下优化代码结构 |

## 八、报错关注模型

### 8.1 报错五类分类法

| 错误类型 | 典型信号 | 第一反应 |
|---------|---------|---------|
| **环境类** | `is required`、`undefined`、`not set` | 不改代码，查环境配置 |
| **依赖类** | `Cannot find module`、`Module not found` | 查package.json + 重装 |
| **逻辑类** | 无明显红字、流程走不到 | 打log看执行路径 |
| **类型类** | `Type X is not assignable to Y` | 对照真实数据修 |
| **接口契约类** | `401/403`、`400 Bad Request` | 对齐接口文档 |

### 8.2 30秒报错定位流程

```
看到红字报错
  │
  ├─ 5s：冷静阅读错误信息，抓关键词
  │
  ├─ 10s：判断错误类别
  │
  ├─ 5s：检查最近改动
  │
  ├─ 5s：快速验证假设
  │
  └─ 持续：制定深入排查计划
```

## 九、人机协作核心原则

### 9.1 人是唯一的舵手

- AI是效率惊人、马力充沛的引擎，但没有人掌舵，船跑得越快偏航风险越大
- 人的职责不是和AI比拼速度，而是**持续判断方向是否正确**

### 9.2 上下文决定输出质量

| 输入方式 | 输出结果 | 本质 |
|----------|----------|------|
| 一句话模糊需求 | "展示型文档"：看似完整但无优先级、无边界 | AI靠猜 |
| 结构化、经过审计的需求 | "交付型文档"：有优先级、有边界、可直接执行 | AI按图索骥 |

## 十、可迁移方法论总结

本方法论适用于任何中等复杂度以上的AI辅助项目：

1. **战略定型**：把"想做什么"变成"明确不做什么"
2. **工程定型**：从"AI帮我写代码"到"AI在我的工程规则里工作"
3. **工程落地**：不再害怕AI改代码，随时可停、查、退

**核心心法**：你拥有的不只是一个项目，而是一条可迁移的AI协作工程路径。能把项目做好，就意味着你学会了如何"驾驭"AI，而不是被AI牵着走。
